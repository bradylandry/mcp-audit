## High

### Subprocess heuristic misclassifies inbound-network listeners
- **File**: `audit/ast_scan.py:375`
- **Issue**: The condition that detects subprocess calls is:
  ```python
  if name in _SUBPROCESS_FUNCS or any(
      name.endswith("." + sp.split(".")[-1])
      for sp in _SUBPROCESS_FUNCS
      if sp.startswith("subprocess")
  ):
  ```
  The `any(name.endswith(...))` clause matches any dotted name whose last component is one of `run`, `call`, `check_call`, `check_output`, `Popen`, `getoutput`, or `getstatusoutput`. Because this `if` block comes before the `elif name in _INBOUND_FUNCS` block, calls to `uvicorn.run(...)`, `hypercorn.run(...)`, `flask.Flask.run(...)`, and `Flask.run(...)` — all members of `_INBOUND_FUNCS` — are consumed by the subprocess branch first. They appear as spurious subprocess findings, and the inbound-network dimension misses them entirely. The test suite does not catch this because `tests/fixtures/bad_mcp/server.py` uses `s.bind(...)` for its inbound test, which is not affected.
- **Fix**: Move the `any(name.endswith(...))` secondary heuristic behind the `_INBOUND_FUNCS` membership check, or (better) restrict it to names whose receiver component is actually `subprocess` (e.g., require `name.startswith("subprocess.")`). Simplest safe fix:
  ```python
  if name in _SUBPROCESS_FUNCS or (
      "." not in name.split(".", 1)[0]  # receiver is a bare name
      and name not in _INBOUND_FUNCS
      and any(name.endswith("." + sp.split(".")[-1])
              for sp in _SUBPROCESS_FUNCS if sp.startswith("subprocess"))
  ):
  ```
  Add a regression test: scan a snippet containing `uvicorn.run(...)` and assert it appears in `inbound_calls`, not `subprocess_calls`.

## Medium

### Dead ternary — bidi-override severity is always "high"
- **File**: `audit/findings.py:338`
- **Issue**: The severity assignment for the zero-width-unicode finding is:
  ```python
  sev: Severity = "high" if bidi_count > 0 else "high"
  ```
  Both branches produce `"high"`. The adjacent comment explicitly states "Plain zero-width chars are usually a hidden-content attack vector but lower-severity than bidi inversion", and the `deduction` variable correctly uses `3` vs `2` to distinguish them — but the severity label does not. As a result, every zero-width character triggers a `high`-severity finding, and a CI gate set to `--max-severity high` would fail even for a minor zero-width space that merits only `medium`.
- **Fix**: Replace the dead ternary with the intended distinction:
  ```python
  sev: Severity = "high" if bidi_count > 0 else "medium"
  ```

### Double scan when `--json` flag is used
- **File**: `audit/cli.py:186-189`
- **Issue**: `main()` calls `scan(target, ...)` unconditionally on line 186, then on line 189 the `--json` branch calls `scan_to_json(target, ...)` which internally calls `scan()` a second time. Every invocation with `--json` therefore walks the entire target directory tree twice and parses every `.py` file twice. For a large MCP package this is a measurable slowdown; for a CI job running on many packages it compounds.
- **Fix**: `scan_to_json` should accept an already-computed `ScanResult` as an optional first argument, or `cli.py` should serialize the existing `scan_result` directly instead of calling `scan_to_json`. For example:
  ```python
  if args.json:
      sys.stdout.write(scan_to_json(target, include_tests=args.include_tests))
  # ↓ replace with:
  if args.json:
      import json as _json
      # reuse scan_result already computed above
      payload = _build_json_payload(scan_result)
      sys.stdout.write(_json.dumps(payload, indent=2))
  ```

### `--ascii` flag documented but not implemented
- **File**: `audit/cli.py:7`
- **Issue**: The module docstring lists `mcp-audit /path --ascii` as a valid invocation, but no `--ascii` argument is added to the `argparse` parser. Running `mcp-audit target --ascii` produces `error: unrecognized arguments: --ascii` and exits 2. Any user or script following the documented usage will get a silent failure.
- **Fix**: Either add `--ascii` to the parser (as a flag that suppresses emoji/UTF-8 in the markdown output, replacing ✅/❌ with `[YES]`/`[NO]`) or remove the entry from the module docstring.

## Low

### `_check_dependencies` only fires when every dependency is unpinned
- **File**: `audit/findings.py:428`
- **Issue**: The loose-pin check is gated by `len(loose) == len(s.dependencies)`:
  ```python
  if loose and len(loose) == len(s.dependencies):
      r.findings.append(...)
  ```
  A package with one pinned dep and four unpinned deps raises no finding at all. A real-world MCP often has exactly one pinned dep (the vendored SDK) and several unpinned transitive helpers — this pattern silently passes.
- **Fix**: Remove the `len(loose) == len(s.dependencies)` guard and always flag when there are any loose deps, adjusting the title to report the count: `f"{len(loose)} of {len(s.dependencies)} dep(s) use loose pins"`.

### `scan_to_json` omits the `open_calls` list
- **File**: `audit/ast_scan.py:689`
- **Issue**: `ScanResult.open_calls` is populated during scanning (it records the raw `open()` call with its mode annotation) but is not serialized in `scan_to_json`. Consumers using `--json` cannot distinguish a bare `open(path)` read from a categorized `Path.read_text()` read, or see the `mode=` annotation without reparsing.
- **Fix**: Add `"open_calls": [_call_dict(c) for c in r.open_calls]` to the `payload` dict in `scan_to_json`.
