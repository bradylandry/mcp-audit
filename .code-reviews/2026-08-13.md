## High

### Subprocess suffix-heuristic false-positives on common patterns
- **File**: `audit/ast_scan.py:375`
- **Issue**: The subprocess detection check has two arms joined by `or`. The first arm is exact: `name in _SUBPROCESS_FUNCS`. The second arm is a suffix match over every entry in `_SUBPROCESS_FUNCS` that begins with `"subprocess"`:
  ```python
  any(name.endswith("." + sp.split(".")[-1]) for sp in _SUBPROCESS_FUNCS if sp.startswith("subprocess"))
  ```
  The suffix set this produces is `{run, call, check_call, check_output, Popen, getoutput, getstatusoutput}`. Any method call whose resolved dotted name ends with `.run`, `.call`, `.check_output`, etc. on **any** receiver is therefore flagged as subprocess — regardless of what the receiver is. Confirmed false-positive cases: `asyncio.run(coro)` (name = `asyncio.run`, ends with `.run`), `flask_app.run()`, `task.call()`, `runner.check_output()`. The existing HTTP heuristic correctly guards against this by requiring the receiver chain to contain a keyword like `session`, `client`, `http`, etc. The subprocess heuristic has no such guard. For a tool whose primary output is a severity score, a false-positive here produces a spurious HIGH finding that drops the score by 2–3 points and may mislead users into distrusting a safe package.
- **Fix**: Mirror the HTTP heuristic approach. After verifying `name in _SUBPROCESS_FUNCS`, drop the open-ended suffix branch entirely (or narrow it to require the receiver chain to contain `subprocess`, `os`, `pty`, or `pexpect`). The exact-match set already covers all the important subprocess entry points; the suffix fallback adds false-positive risk without covering a documented gap.

## Medium

### Double scan when `--json` flag is used
- **File**: `audit/cli.py:186–190`
- **Issue**: In `main()`, `scan()` is always called unconditionally at line 186 (`scan_result = scan(target, include_tests=args.include_tests)`). When the user passes `--json`, `scan_to_json()` is then called at line 189, which internally calls `scan()` a second time from scratch. The result of the first scan is discarded. For large packages this doubles the file-walk and AST-parse time. Worse, if the package directory changes between the two scans (e.g., a `pip install` racing against the audit), the two scans could produce different results while the CLI emits only the second one.
- **Fix**: Refactor so `--json` serialises the already-computed `scan_result` instead of re-scanning. `scan_to_json` can accept an optional pre-computed `ScanResult`; alternatively, extract a `_result_to_dict` helper and call it from both code paths.

### Silent SyntaxError skip gives no scan-coverage feedback
- **File**: `audit/ast_scan.py:671–672`
- **Issue**: When `ast.parse()` throws `SyntaxError` (e.g., encoding errors survive the `errors="replace"` read, a file uses a syntax feature not supported on the running Python version, or a file is intentionally obfuscated), the file is silently skipped with `continue`. The `files_scanned` counter is not incremented for that file, but there is also no `files_failed` counter, no warning to stderr, and nothing in the `ScanResult` to signal that coverage was incomplete. A user auditing a package with 10 files could receive a scan that only covered 7 — with no indication that 3 files were missed.
- **Fix**: Add a `files_skipped: int = 0` field to `ScanResult`. Increment it on `SyntaxError`. Emit a `# WARNING: N file(s) failed to parse` line in the markdown report header when `files_skipped > 0`, and include the field in JSON output.

### Loose dep-pin finding silently drops when any dep has an exact pin
- **File**: `audit/findings.py:428–440`
- **Issue**: The condition for emitting `MCP011` is `if loose and len(loose) == len(s.dependencies)`. The second clause means the finding is only emitted when **every** declared dependency is loosely pinned. If a package declares `["requests", "httpx>=0.25", "pydantic==2.0"]`, two of three deps are loose and no finding fires — a silent false-negative. The finding title also says "All N dep(s) use loose version pins," which overstates the check: it reports on all deps but only actually catches the all-loose case.
- **Fix**: Remove the `len(loose) == len(s.dependencies)` guard. Fire `MCP011` whenever `len(loose) > 0`. Update the title to accurately describe how many are loose vs. total, e.g., `f"{len(loose)} of {len(s.dependencies)} dep(s) use loose version pins"`.

### Dep parsing silently skipped on Python 3.10 with no warning
- **File**: `audit/ast_scan.py:578–584`
- **Issue**: `pyproject.toml` declares `requires-python = ">=3.10"`, but `tomllib` is stdlib only from Python 3.11. On 3.10, `_parse_deps` returns an empty list with a descriptive `dep_source` string (`"pyproject.toml (3.11+ required for full parse)"`), and no warning is ever emitted. The `MCP011` (loose pins) and the dependency capabilities section are both silently absent. A user on Python 3.10 gets a higher-than-warranted score for any package with loose pins, without knowing why.
- **Fix**: Either add `tomli` as an optional install extra for Python < 3.11 and import it conditionally, or emit a `sys.stderr.write("warning: dep parsing requires Python 3.11+...\n")` in the fallback branch so the gap is visible. The `dep_source` string already carries the right message — it just needs to also appear somewhere in the rendered output when deps are empty due to this condition.

### Dead-branch severity variable in zero-width unicode check
- **File**: `audit/findings.py:338`
- **Issue**: The ternary `sev: Severity = "high" if bidi_count > 0 else "high"` assigns `"high"` in both branches, making the condition dead code. The inline comment says "Bidi-override chars are higher severity" implying the original intent was to differentiate bidi from plain zero-width chars (the deductions do differ: 3 vs. 2), but the severity label was left identical. The dead ternary creates a misleading reading of the code.
- **Fix**: If both should be "high", remove the ternary: `sev: Severity = "high"`. If the intent was a differentiated label (e.g., plain zero-width → `"medium"`, bidi-override → `"high"`), update accordingly and reconcile with the README's scoring table.

### Stale hardcoded default in `render_markdown` signature
- **File**: `audit/report.py:15`
- **Issue**: `def render_markdown(r: AuditReport, tool_version: str = "0.1.0") -> str:` — the default is `"0.1.0"` but the package is at `0.3.0`. Every call from the CLI passes the real version, so production output is unaffected, but any caller that omits `tool_version` (e.g., tests calling `render_markdown(rep)` directly) embeds a stale version in rendered output.
- **Fix**: Change the default to `"unknown"` or remove the default and require the caller to pass it. In `test_render_markdown_returns_non_empty_for_clean`, the call at line 613 omits `tool_version`, so the rendered report says "mcp-audit v0.1.0" — update the call to pass the real version or a sentinel.

### `_is_path_write` is a permanent no-op stub
- **File**: `audit/ast_scan.py:549–554`
- **Issue**: `_is_path_write` always returns `False` and is documented as a placeholder "for additional Path-variant patterns we add later." It has existed through at least v0.1–v0.3 without being implemented. The method is called in the hot path of `visit_Call` for every AST node, adding overhead without effect.
- **Fix**: If no additional Path patterns are needed (since `Path.write_text` etc. are already in `_FS_WRITE_FUNCS`), delete the method and its call site at line 419. If extension is planned, file it as a tracked issue rather than leaving inert code in the hot path.

### TLS capability gap when all TLS-off calls are suppressed
- **File**: `audit/findings.py:163–168`
- **Issue**: After filtering suppressed calls with `_not_suppressed`, if `tls_off` is empty (all calls suppressed) but `s.tls_disabled_calls` is non-empty, neither the "TLS off" finding nor the "TLS on" capability entry is appended. The capabilities section is silent on TLS posture, which is confusing — a reader of the report cannot tell whether TLS was fine or whether a finding was acknowledged.
- **Fix**: Add an explicit `elif` for the suppressed-but-acknowledged case:
  ```python
  elif not tls_off and s.tls_disabled_calls:
      r.capabilities_no.append(
          "TLS verification disabled on some calls — suppressed via inline directive"
      )
  ```
