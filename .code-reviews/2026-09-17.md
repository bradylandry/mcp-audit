## Medium

### Severity ternary in `_check_string_content` has both branches identical — bidi vs. zero-width distinction is lost
- **File**: `audit/findings.py:338`
- **Issue**: `sev: Severity = "high" if bidi_count > 0 else "high"` — both branches evaluate to `"high"`. The surrounding comment ("Bidi-override chars are higher severity... Plain zero-width chars are usually a hidden-content attack vector but lower-severity than bidi inversion") makes the original intent clear: bidi-override should be "high" and plain zero-width should be "medium". The deduction does differ (3 vs 2), but the severity label is identical for both. Report consumers that gate on severity (e.g., `--max-severity medium`) will never see zero-width findings at lower severity than bidi ones, defeating the discrimination. Any test that checks `sev == "medium"` for a zero-width-only finding would also silently fail.
- **Fix**: `sev: Severity = "high" if bidi_count > 0 else "medium"`.

### Subprocess detection heuristic false-positives on non-subprocess `.run()` calls
- **File**: `audit/ast_scan.py:375`
- **Issue**: The condition `any(name.endswith("." + sp.split(".")[-1]) for sp in _SUBPROCESS_FUNCS if sp.startswith("subprocess"))` generates suffix patterns like `.run`, `.call`, `.check_call`, etc. and matches any dotted name ending in them. `uvicorn.run`, `hypercorn.run`, `mcp.run`, and `FastMCP.run` all match `.run` — but `uvicorn.run` and `hypercorn.run` are also in `_INBOUND_FUNCS`, so they would be double-classified as both subprocess and inbound-network. `FastMCP.run()` (the standard MCP server launch) would be flagged as subprocess, which is misleading and contradicts the `# mcp-audit: ignore MCP001` suppression pattern already in use in jarvis-trading-mcp. This will produce false-positive subprocess findings on any MCP server that calls `mcp.run()` without a suppression directive.
- **Fix**: Remove the broad `any()` suffix heuristic. The exact `_SUBPROCESS_FUNCS` catalog already covers `subprocess.*` and `os.*` variants comprehensively. Any missed pattern (e.g., `subprocess.Popen` called as an attribute on an aliased import) should be added explicitly to the catalog rather than caught by a suffix wildcard.

### `_is_path_write` is a documented no-op that provides false confidence
- **File**: `audit/ast_scan.py:549`
- **Issue**: `_is_path_write()` always returns `False` with a comment that it's "a hook for additional Path-variant patterns we add later." The calling condition in `visit_Call` (line 419) is `elif name in _FS_WRITE_FUNCS or self._is_path_write(name)`. If `_is_path_write` ever returns True for a name that IS already in `_FS_WRITE_FUNCS`, the short-circuit `or` prevents the second branch from mattering; if it returns True for a name that is NOT in `_FS_WRITE_FUNCS`, the `elif` branch would incorrectly skip the `_FS_WRITE_FUNCS` catalog check. Currently harmless (always False), but the scaffolding is misleading and would require careful logic review before use.
- **Fix**: Remove the method and the dead `or self._is_path_write(name)` arm. Add new Path patterns directly to `_FS_WRITE_FUNCS` when needed, which is the pattern used for all other catalogs.
