## Medium

### Dead severity branch in `_check_string_content` — bidi vs ZWSP distinction is lost
- **File**: `audit/findings.py:338`
- **Issue**: The code reads:
  ```python
  sev: Severity = "high" if bidi_count > 0 else "high"
  ```
  Both the `if` and `else` branches assign `"high"`, making the condition meaningless. The inline comment says *"Plain zero-width chars are usually a hidden-content attack vector but lower-severity than bidi inversion"*, but the code assigns identical severity to both. Bidi-override characters (used in CVE-2021-42574 "Trojan Source") are materially more dangerous than plain zero-width spaces. The intended behavior — `"medium"` for plain ZWSP, `"high"` for bidi-override — is documented but not implemented.
- **Fix**:
  ```python
  sev: Severity = "high" if bidi_count > 0 else "medium"
  deduct = 3 if bidi_count > 0 else 2
  ```
  Also add a test to `TestStringContentSafety` that asserts a plain-ZWSP-only string scores `"medium"` severity (currently there's no test locking in the distinction). Note: the `deduct` value already differs correctly (3 vs 2) — only `sev` is broken.

## Low

### Subprocess heuristic's `any(...)` clause has broad false-positive surface
- **File**: `audit/ast_scan.py:375`
- **Issue**: The subprocess detection condition is:
  ```python
  if name in _SUBPROCESS_FUNCS or any(name.endswith("." + sp.split(".")[-1]) for sp in _SUBPROCESS_FUNCS if sp.startswith("subprocess")):
  ```
  The `any(...)` clause matches any attribute access whose name ends in `.run`, `.call`, `.Popen`, etc., regardless of receiver. `asyncio.run(...)` resolves to `name = "asyncio.run"` which ends in `.run` and would match. In practice `asyncio.run` isn't in the current test fixtures so no tests have caught it, but it will produce false-positive findings on any MCP that uses async entrypoints.
- **Fix**: Add the known safe receivers to an exclusion list, or restrict the heuristic to only fire when the receiver name contains `subprocess`/`os`/`pty`/`pexpect`. The simplest fix is to replace the `any(...)` clause with explicit catalog entries for the cases it's meant to catch, rather than a suffix-match heuristic.

### `_is_path_write` is dead code
- **File**: `audit/ast_scan.py:549`
- **Issue**: `_is_path_write` unconditionally returns `False`. The comment says it's a "hook for additional Path-variant patterns we add later" but this has been present since v0.1 and the function is never non-trivially true. It's called in `visit_Call` (`elif name in _FS_WRITE_FUNCS or self._is_path_write(name)`) so its presence isn't harmful, but it adds false documentation burden — readers must understand why a method exists that always returns False.
- **Fix**: Delete the method and the `or self._is_path_write(name)` call site. If Path write variants need to be added later, extend `_FS_WRITE_FUNCS` directly.

### `_SEVERITY_RANK` includes `"info"` but `--max-severity` choices don't
- **File**: `audit/cli.py:100`, `audit/cli.py:159`
- **Issue**: `_SEVERITY_RANK = {"info": 0, "low": 1, "medium": 2, "high": 3}` but `--max-severity` choices are `["low", "medium", "high"]`. This is minor (argparse prevents the "info" choice from being passed), but creates a small documentation mismatch: the dict implies "info" is a valid threshold, and future code that calls `_exit_code_from_max_severity` programmatically with `"info"` would silently accept it and exit 1 for every finding — unexpected behavior.
- **Fix**: Either add `"info"` to the `--max-severity` choices (probably not useful for CI gates), or remove it from `_SEVERITY_RANK` and handle the `threshold_rank < 0` path explicitly in `_exit_code_from_max_severity`. The simplest: restrict the dict to the three choices that actually appear in the CLI: `_SEVERITY_RANK = {"low": 1, "medium": 2, "high": 3}`.
