## High

### _check_string_content severity conditional is a dead branch
- **File**: `audit/findings.py:338`
- **Issue**: The line `sev: Severity = "high" if bidi_count > 0 else "high"` always evaluates to `"high"` — both branches are identical. The surrounding comment says "Plain zero-width chars are usually a hidden-content attack vector but lower-severity than bidi inversion," clearly expressing intent that plain zero-width chars should be rated below bidi-overrides. The deduction IS differentiated (`deduct = 3 if bidi_count > 0 else 2`), but severity is not. As a result, every zero-width finding — even an innocuous stray zero-width space — fires at `"high"` severity, which means `--max-severity high` CI gates will fail on false positives. Any package with an accidental zero-width character in a long docstring will score 2 points lower and surface a "high" finding.
- **Fix**: Change the else branch: `sev: Severity = "high" if bidi_count > 0 else "medium"`. This matches the documented intent, differentiates the two cases in finding output, and makes the CI gate behavior sensible.

### --ascii flag documented but not implemented
- **File**: `audit/cli.py:11`
- **Issue**: The module-level docstring lists `mcp-audit /path/to/mcp/package --ascii` as a valid usage pattern. No `--ascii` argument is added to the argparse parser in `main()`. Users who try `mcp-audit path --ascii` receive `error: unrecognized arguments: --ascii` — an unhelpful argparse error that makes it look like the tool is broken. There is also no test covering this, so the stale documentation has persisted undetected.
- **Fix**: Either (a) implement `--ascii` (strip emoji from output — likely the intended meaning, since the UTF-8 reconfiguration comment addresses Windows console issues), or (b) remove `--ascii` from the docstring. If implementing, add `parser.add_argument("--ascii", action="store_true", help="...")` and in `render_markdown`, substitute emoji (✅/❌) with ASCII equivalents when the flag is set.

## Medium

### _check_dependencies only fires when ALL deps are loose-pinned
- **File**: `audit/findings.py:428-441`
- **Issue**: The condition `if loose and len(loose) == len(s.dependencies)` only triggers the "loose version pins" finding when every single dependency is unpinned. A package with 9 pinned deps and 1 loose dep produces no finding, even though the one loose dep is an upgrade vector. The README's "Scoring methodology" section says "loose pins (no ==)" without this qualification, creating a contract mismatch. The finding is also `deduction=0`, so it doesn't affect the score regardless — but it should at least appear in the report for awareness.
- **Fix**: Change the condition to `if loose:` and update the title from `f"All {len(loose)} dep(s) use loose version pins"` to `f"{len(loose)} of {len(s.dependencies)} dep(s) use loose version pins"`. This makes the finding fire whenever any dep is loose, matching the documented behavior.
