## High

### Subprocess false-positive: `.run()` matches `mcp.run()`, `asyncio.run()`, `app.run()`
- **File**: `audit/ast_scan.py:376`
- **Issue**: The secondary subprocess detection heuristic is:
  ```python
  any(name.endswith("." + sp.split(".")[-1]) for sp in _SUBPROCESS_FUNCS if sp.startswith("subprocess"))
  ```
  `subprocess.run` → suffix `".run"`. Any call whose dotted name ends with `.run` — including `mcp.run()`, `asyncio.run()`, `server.run()`, `app.run()`, `loop.run()` — matches this condition and is classified as a subprocess call. Since FastMCP-based MCP servers (the most common pattern) all end their entrypoint with `mcp.run()`, every such server gets a false MCP001 finding and a −2 score deduction. The test suite doesn't cover this because the fixture servers use `if __name__ == "__main__": mcp.run()` patterns that currently escape detection only by coincidence (the fixture `server.py` for clean_mcp may not include a `mcp.run()` call). The intent of the heuristic — catching e.g. `proc.run(...)` where `proc` is a `subprocess.Popen` instance — is sound, but the suffix match is too broad.
- **Fix**: Narrow the suffix match to require that the receiver name looks like a subprocess object, similar to the HTTP client heuristic's `http_signals` check:
  ```python
  # In visit_Call, replace the broad suffix check with:
  if name in _SUBPROCESS_FUNCS:
      # existing logic
  elif "." in name:
      tail = name.rsplit(".", 1)[-1]
      receiver = name.rsplit(".", 1)[0].lower()
      subprocess_signals = ("proc", "process", "popen", "child", "pipe")
      if tail in {"run", "call", "popen"} and any(sig in receiver for sig in subprocess_signals):
          # flag as subprocess
  ```
  Or more simply: remove the secondary heuristic entirely. The exact-match catalog already covers `subprocess.run`, `subprocess.Popen`, `os.system`, etc. — the suffix heuristic adds false positives without meaningfully improving detection.

## Medium

### Dead-code ternary: zero-width severity is always "high" regardless of bidi
- **File**: `audit/findings.py:338`
- **Issue**:
  ```python
  sev: Severity = "high" if bidi_count > 0 else "high"
  ```
  Both branches return `"high"`. The surrounding comments explain the intended distinction: bidi-override chars (CVE-2021-42574 / Trojan Source) deserve higher severity than plain zero-width spaces; deductions are set to 3 vs. 2 accordingly. But the `sev` variable is used only in the `Finding` and the comment's intent ("bidi-override chars are higher severity") is never actually realized — all zero-width findings are reported as the same "high" severity regardless. The `deduct` variable is correctly differentiated (3 vs. 2), but `sev` is not.
- **Fix**:
  ```python
  sev: Severity = "high"  # bidi-override and plain zero-width are both high severity
  deduct = 3 if bidi_count > 0 else 2
  ```
  Or if a two-tier severity is desired (and the README is updated to match):
  ```python
  sev: Severity = "high" if bidi_count > 0 else "medium"
  deduct = 3 if bidi_count > 0 else 1
  ```
