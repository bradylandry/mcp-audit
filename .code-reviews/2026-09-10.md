## High

### Overly broad subprocess heuristic false-positives on `asyncio.run`, `app.run`, and any `.run()` or `.call()` method
- **File**: `audit/ast_scan.py:375`
- **Issue**: The second arm of the subprocess detection condition uses suffix matching against method names extracted from `_SUBPROCESS_FUNCS`. This generates the suffix set `{'.run', '.call', '.check_call', ...}` and matches any dotted name ending in one of those. `asyncio.run` → True, `app.run` → True, `flask.Flask.run` → True, `some.obj.call` → True. A standard asyncio-based MCP server (`asyncio.run(main())`) would receive a spurious high/medium subprocess finding, degrading its score by 2–3 points with no legitimate basis.
- **Fix**: Remove the second arm entirely. The first arm (`name in _SUBPROCESS_FUNCS`) already covers every named subprocess pattern. If the intent was catching locally-aliased subprocess modules, that requires flow analysis not achievable statically. Alternatively, gate the heuristic on receiver names that actually suggest subprocess usage (e.g. receiver contains `proc`, `process`, `subprocess`), mirroring the guard in `_is_http_client_call`.

### Dead ternary branch — `_check_string_content` severity never differs between bidi-override and plain zero-width
- **File**: `audit/findings.py:338`
- **Issue**: Both branches of the ternary evaluate to the same literal: `sev: Severity = "high" if bidi_count > 0 else "high"`. The comment above says "Plain zero-width chars are usually a hidden-content attack vector but lower-severity than bidi inversion." The `deduction` IS differentiated (3 vs 2) so the score impact is partially correct, but the severity label is always `"high"` regardless. Any consumer of the JSON report that gates on `severity == "medium"` for plain zero-width characters would never trigger.
- **Fix**: Replace `else "high"` with `else "medium"` as the surrounding documentation intends.

## Medium

### `_check_dependencies` silently skips loose-pin findings when even one dep is pinned
- **File**: `audit/findings.py:428`
- **Issue**: `if loose and len(loose) == len(s.dependencies):` — the finding only fires when every declared dependency has a loose pin. A package with 9 unpinned deps and one pinned dep produces zero findings for the 9 unpinned ones. A partial loose-pinning situation is still a real supply-chain risk that the tool silently drops.
- **Fix**: Change the condition to `if loose:` and update the finding title to reflect the actual count, e.g. `f"{len(loose)} of {len(s.dependencies)} dep(s) use loose version pins"`.

### `--json` flag re-runs the scan a second time instead of reusing the already-computed result
- **File**: `audit/cli.py:189`
- **Issue**: `scan_result` is computed on line 186, but `--json` discards it and calls `scan_to_json(target, ...)` which invokes `scan()` again from scratch. For large packages this doubles wall time. More importantly, if any file is modified between the two calls (possible in CI), the JSON output could differ from the scan that feeds `build_report`.
- **Fix**: Refactor `scan_to_json` to accept a `ScanResult` object (or expose a JSON-serialization helper separately), then call it as `_scan_result_to_json(scan_result)` using the already-computed result.

## Low

### `_is_path_write` is a permanent stub that always returns `False`
- **File**: `audit/ast_scan.py:549`
- **Issue**: The method body is `return False` with a comment "hook for additional Path-variant patterns we add later." It's referenced in the hot path of `visit_Call` on every single AST node visit while contributing nothing. Suggests additional Path patterns were planned but never implemented, creating a false sense of completeness.
- **Fix**: Either implement the method or remove the call site and the stub. If `Path(...).write_text` detection is needed, verify that existing `_FS_WRITE_FUNCS` entries cover it and remove the dead hook.

### Missing explicit parentheses in inbound-network detection condition
- **File**: `audit/ast_scan.py:471`
- **Issue**: `elif name in _INBOUND_FUNCS or bare in ("bind",) and self._looks_like_socket_bind(node):` — Python's `and > or` precedence produces the correct grouping, but without explicit parentheses the condition reads as ambiguous. A future editor restructuring the condition could silently change semantics.
- **Fix**: Add explicit parentheses: `elif name in _INBOUND_FUNCS or (bare in ("bind",) and self._looks_like_socket_bind(node)):`.

### `yaml.BaseLoader` listed as a "safe" loader in the deserialization allow-list
- **File**: `audit/ast_scan.py:366`
- **Issue**: `BaseLoader` does not resolve YAML type tags but is not equivalent to `SafeLoader` — it lacks the tag-based ACE prevention. Auditors who see `yaml.load(text, Loader=yaml.BaseLoader)` flagged as safe may conclude the call poses no deserialization risk when the code origin is untrusted.
- **Fix**: Remove `yaml.BaseLoader` and `BaseLoader` from `safe_loaders`. Document in a comment that only `SafeLoader` / `CSafeLoader` are considered fully safe for untrusted input.

### `Path` imported inside `_guess_package_name` rather than at module level
- **File**: `audit/report.py:147`
- **Issue**: `from pathlib import Path` appears inside the body of `_guess_package_name`. Inline function-level imports obscure the module's actual dependencies from static analysis tools and execute on every call rather than once at module load.
- **Fix**: Move `from pathlib import Path` to the top-level imports of `report.py`.
