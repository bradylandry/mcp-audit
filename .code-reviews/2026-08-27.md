## High

### Subprocess detection: overbroad name-suffix matching produces false positives
- **File**: `audit/ast_scan.py:375`
- **Issue**: The subprocess detection condition is:
  ```python
  if name in _SUBPROCESS_FUNCS or any(
      name.endswith("." + sp.split(".")[-1])
      for sp in _SUBPROCESS_FUNCS
      if sp.startswith("subprocess")
  ):
  ```
  The suffix set derived from `_SUBPROCESS_FUNCS` includes the bare names `run`, `call`, `check_call`, `check_output`, `Popen`, `getoutput`, `getstatusoutput`. Any dotted call whose final component matches one of these — `model.run()`, `scheduler.call()`, `pipeline.check_output()`, `trainer.Popen()` — is flagged as a subprocess call, regardless of receiver. This is the same class of false-positive that was explicitly fixed for HTTP client calls (the `_is_http_client_call` receiver-signal heuristic exists for exactly this reason). False positives in a security audit tool erode trust and can crowd out genuine findings.
- **Fix**: Apply the same receiver-signal guard used by `_is_http_client_call`. Build a `_is_subprocess_call(name)` helper that requires the receiver to contain `subprocess`, `proc`, `shell`, `os`, `pty`, or `pexpect` before matching bare-verb suffixes. Alternatively, remove the suffix-matching branch entirely — `_SUBPROCESS_FUNCS` already contains the fully-qualified names (`subprocess.run`, `os.system`, etc.) that `_dotted_name` resolves to, so the suffix heuristic adds no true-positive value for well-typed code.

## Medium

### Double scan in `--json` branch
- **File**: `audit/cli.py:186-189`
- **Issue**: `scan()` is called unconditionally at line 186 for every code path, then `scan_to_json()` (which calls `scan()` internally) is called at line 189 when `--json` is active. The `scan_result` from line 186 is discarded and never used in the `--json` branch. For large MCP packages this doubles scanning time and peak memory.
- **Fix**: Replace the unconditional `scan_result = scan(...)` with a lazy pattern, or refactor `scan_to_json` to accept an already-computed `ScanResult`. Simplest fix: delete the outer `scan()` call and handle the `--json` branch first, since `scan_to_json` returns the raw JSON directly:
  ```python
  if args.json:
      sys.stdout.write(scan_to_json(target, include_tests=args.include_tests))
      sys.stdout.write("\n")
      return 0
  scan_result = scan(target, include_tests=args.include_tests)
  ```

### Dead conditional gives plain zero-width unicode and bidi-override the same severity
- **File**: `audit/findings.py:338`
- **Issue**: `sev: Severity = "high" if bidi_count > 0 else "high"` — both branches evaluate to `"high"`. The comment two lines above says "Plain zero-width chars are usually a hidden-content attack vector but lower-severity than bidi inversion", and the `deduct` variable correctly gives 3 vs 2. The severity variable is a no-op ternary; the intended else value is almost certainly `"medium"`. As written, plain ZWSP in a string is reported at the same severity as a Trojan Source / bidi-override attack (CVE-2021-42574 class), which overstates the risk and will cause CI gating (`--max-severity=medium`) to miss the intended escalation difference.
- **Fix**: Change to `sev: Severity = "high" if bidi_count > 0 else "medium"`.

### Dependency finding silently skips partially-unpinned sets
- **File**: `audit/findings.py:428`
- **Issue**: `if loose and len(loose) == len(s.dependencies):` — the finding only fires when every declared dependency lacks an `==` pin. A package with 9 loose deps and 1 pinned dep raises no finding at all. The finding title says "All X dep(s) use loose version pins" which implies the condition is deliberate, but the docstring rationale ("so a future transitive update can't change behavior") applies equally to any loose dep, not only when all are loose. Users auditing a package that is almost entirely unpinned get no signal.
- **Fix**: Either (a) raise the finding whenever any dep is loose (changing the title and detail to list which ones are loose), or (b) lower the threshold to, e.g., `>= 50%` loose. At minimum, add a comment explaining why 100% is the chosen threshold so future maintainers know it is intentional.

## Low

### Stale `--ascii` flag documented in CLI module docstring but never implemented
- **File**: `audit/cli.py:9`
- **Issue**: The module-level docstring lists `mcp-audit /path/to/mcp/package --ascii` as a valid invocation. No `--ascii` argument is added to the `argparse.ArgumentParser`. Running `mcp-audit --ascii` produces an argparse error (`unrecognized arguments: --ascii`), which is confusing for users who read the help text.
- **Fix**: Either implement `--ascii` (strip emoji, output plain ASCII ✓/✗) or remove it from the docstring.

### Scoring methodology footer misclassifies broad-credential env reads as High
- **File**: `audit/report.py:116`
- **Issue**: The rendered "Scoring methodology" section says: `"High (−2 to −3 each): subprocess with shell=True, dynamic exec, TLS verification disabled, suspicious env var reads"`. But `_check_env_vars` in `findings.py` classifies `BROAD_CREDENTIAL_ENV` as `severity="medium"` with `deduction=1`. A reader using the footer to interpret their report will think a broad-credential finding is high-severity when it is actually medium.
- **Fix**: Move "suspicious env var reads" to the Medium bullet in the methodology footer.

### `_call_dict` drops suppression metadata from raw JSON output
- **File**: `audit/ast_scan.py:718-719`
- **Issue**: `_call_dict` returns `{"file": c.file, "line": c.line, "name": c.name, "note": c.note}` — it omits `suppressed_rules`. When a consumer uses `--json` to extract raw call sites, suppression directives are invisible. A CI script post-processing the raw JSON cannot distinguish a genuine call from a suppressed one, potentially under-counting risks.
- **Fix**: Add `"suppressed_rules": sorted(c.suppressed_rules)` to `_call_dict`'s return value, or add a separate `"suppressions"` key in `scan_to_json`'s payload that mirrors what `--json-report` already exposes.

### `yaml.BaseLoader` listed alongside `yaml.SafeLoader` as a safe YAML loader
- **File**: `audit/ast_scan.py:365-366`
- **Issue**: `safe_loaders = {"yaml.SafeLoader", "SafeLoader", "yaml.CSafeLoader", "CSafeLoader", "yaml.BaseLoader", "BaseLoader"}`. `yaml.BaseLoader` does not resolve Python-specific tags (which is good) but is not equivalent in safety to `SafeLoader` — it loads all scalars as strings without validation, and some YAML libraries document it only as "less unsafe" rather than safe. Treating it as safe suppresses the `yaml.load` finding when `BaseLoader` is used, potentially giving false confidence.
- **Fix**: Remove `"yaml.BaseLoader"` and `"BaseLoader"` from `safe_loaders`. If `BaseLoader` is intentionally included, add a comment referencing the specific threat model under which it is considered safe enough to suppress.
